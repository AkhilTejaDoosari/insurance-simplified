# P2 Evidence Sufficiency and Plan Identity Review

**Status:** Local diagnostic/design review; no production changes. **Scope:** The exact saved compact Sonnet response and original FEP Blue Focus PDF text for pages 1, 17, and 31. No provider requests or PDF transmission were made for this review.

## Executive finding

The compact response is complete and its citation quotes occur on the cited pages, but occurrence verification is not semantic or applicability proof. The response contains eight scoped values: none satisfies the requested all-material-claims-supported bar for `SAFE`; seven are `INCOMPLETE`; and one is `UNSUPPORTED` as a complete claim because its broad exclusion list is not established by the attached evidence. Numeric amounts are generally present on the cited page, but values are not uniformly supported by their particular quotes, and page 17 expressly disclaims being the official statement of benefits. No value should be promoted from this response as-is.

The plan-name failure has two separate causes: the compact validator requires a literal name substring, so `FEP Blue Focus` does not match `FEP® Blue Focus`; production `attestPlans` independently recognizes only its existing explicit first-page declaration/title patterns, none of which matches this brochure title. Citation shape and quote occurrence succeeded; PDF punctuation normalization is not the root cause. Keep production attestation, source verification, and C6 fail-closed behavior intact.

## 2. Plan identity: exact root cause

### Compact validator

`nonstandard/p2-compact-spike/compact-candidate.ts` checks whether any evidence quote lowercased includes the proposed plan name lowercased. The model proposed `FEP Blue Focus`; its quotes were `FEP® Blue Focus` and `131 FEPBlue Focus - Self Only`. Neither contains that exact string. It therefore emits `PLAN_NAME_NOT_IN_EVIDENCE` even though the first-page title contains a visually and semantically matching name. This is an overly literal compact name/evidence check, not a failed citation occurrence check.

### Production attestor

`app/lib/extraction/plan-identity.ts` scans only first-page lines, then accepts explicit `Policy name:` / `Plan name:` declarations and a small set of specific title forms (student insurance, Seven Corners, and a specially labeled program title). The FEP first-page line `FEP® Blue Focus` matches none of these patterns. The attestor therefore returns zero plans. This is a title/declaration-recognition coverage gap, corroborated by the prior unseen-document report; it is not caused by a wrong page, missing citation source, or failed text normalization.

The compact response's `d` and `[page, quote]` evidence shape was structurally valid, and all 14 quote occurrences were verified. Production plan objects, however, require `sources` with `documentId`, page, and quote and still undergo independent plan validation and attestation. Do not turn compact `e` directly into an attested plan.

### Smallest document-agnostic correction to consider

After owner approval, extend first-page attestation with a **conservative generic title-context path** that recognizes a source-cited standalone plan name in the document's actual title block, while retaining current explicit declarations, first-page-only scope, and independent verified-source requirements. Use source text/layout context and conservative token normalization (e.g. trademark marks/punctuation may be ignored for comparison), but do not accept a name merely because it appears somewhere on the page. Never consult the filename. Do not equate enrollment codes with distinct plans. Before adoption, add positive/negative tests for FEP and unseen/non-plan/program documents, ambiguous title blocks, multiple first-page names, and punctuation/registered-mark variants. Keep compact structural validation separate from production identity attestation.

## 3. Citation occurrence versus semantic sufficiency

`verifyEvidenceCitation` validates document ID, page bounds, non-empty page text and quote, then searches for a unique normalized contiguous occurrence (including bounded line-wrap hyphenation/ellipsis handling). It returns the canonical source span. It does **not** decide whether that span entails the model's value, which nearby sentence supplies a scope, whether a qualifier binds to a particular number, or whether a document-level caveat limits use of the page. `checkDisplayGrounding` is a material-token/numeric grounding check, not a benefit-semantic or eligibility model.

Existing `qualifierHasEvidence` provides a useful fail-closed precedent for select qualifier fields: it checks whether qualifier wording appears in the same cited clause as the number. It is not a universal semantic sufficiency check and its current recognized qualifier set does not represent all compact keys (enrollment, exclusions, exceptions, service). Do not generalize it into a universal insurance regex or treat a passing substring match as coverage proof.

### Minimal evidence-sufficiency gate (design only)

For each candidate value, preserve the canonical verified quote(s) and require a typed, auditable review result for each claim dimension:

1. **Numeric/value:** the claimed amount, unit, percentage, range, and cost basis occur and bind to the subject (not another amount in a multi-figure paragraph).
2. **Benefit/cost subject:** source wording identifies the service, benefit, cost share, deductible, or limit described by the candidate.
3. **Enrollment applicability:** explicit enrollment category is attached to the amount/subject; never inherit from a neighboring candidate without its own supporting passage.
4. **Network/provider context:** provider/facility/program and in-/out-of-network or Preferred context are retained only when tied to that claim.
5. **Exclusions/exceptions/conditions:** every asserted exception or excluded expense has evidence; incomplete enumerations are not presented as exhaustive.
6. **Document-level caveat:** disclaimers or cross-references that limit the authority/completeness of the cited section are surfaced as evidence limitations or require the referenced authoritative passage.

Each dimension should be `supported`, `unsupported`, `not_applicable`, or `unresolved`, with source spans and a reason. Promotion requires all applicable dimensions supported. The initial implementation should be a narrowly scoped fail-closed contract with typed per-claim evidence and targeted tests—not a universal semantic classifier. Cases requiring cross-sentence/table interpretation or unavailable referenced pages should remain unresolved for review. These statuses are a proposed diagnostic/gate representation, not a change to the production schema.

## 5. Smallest proposed implementation slice

No implementation is made in this phase. After approvals, the smallest safe slice is a local, provider-free adapter/gate over saved compact fixtures:

1. Validate envelope and manifest IDs; verify all citations and replace candidate quotes with canonical source spans.
2. Apply an explicit reviewed concept/key allowlist. Unknown concepts/qualifiers fail closed to rejection or unresolved diagnostics; no lossy normalization.
3. Add typed per-claim evidence-sufficiency checks for the supported subset, initially requiring source-attested number, subject, enrollment, network and caveat context. Exception/exclusion claims must have their own supporting source spans; don't infer them from a generic amount citation.
4. Add a conservative generic first-page title-context attestation path for plan identity, with corpus-wide false-positive tests. Keep `attestPlans` authoritative and do not add filename inference.
5. Convert only candidates with a lossless mapping to the current v1 contract. Run unchanged `validateTable`, citation verification, plan ownership/attribution, and C6 gates. Unsupported candidates remain unresolved/rejected; no C6 bypass.
6. Demonstrate against the saved FEP response and negative/unseen fixtures before requesting any new provider evaluation. This design phase authorizes no replay.

This slice should not expand into dynamic grouping, UI changes, a new universal semantic engine, schema changes, or alterations to citation/C6 semantics.

## 6. Required approvals

- **Owner approval before any production source, prompt, schema, UI, or C6 change.** This report itself changes none of those.
- **Owner decision on unresolved compact concepts and scope fields.** Existing v1 cannot losslessly carry enrollment, exclusions, exceptions, and several open-vocabulary concepts. A requirement to display/persist them entails an explicit schema/product decision; otherwise those candidates remain rejected/unresolved.
- **Owner approval for generic plan-title attestation changes** and their false-positive criteria. Keep first-page/source-evidence constraint; no filename inference; preserve one plan with enrollment configurations, not three plans.
- **Separate phase approval** for any dynamic fact grouping or user-visible changes, as required by `PLAN.md`.
- **Separate authorization for any future provider request or PDF transmission.** None is part of the proposed local fixture-gate slice.

## 7. Remaining risks

- Text occurrence and token grounding do not establish semantic entailment or applicability.
- Page 17 is explicitly non-authoritative for benefit details; pages 27, 29, 63, and 86 are referenced but outside the permitted selected pages. This review must not claim those terms are authoritative or complete.
- The current production qualifier checks cover a subset of qualifier semantics and cannot represent all compact dimensions.
- A generic title recognizer may create false positives or merge ambiguous identities; strict source/page constraints and negative corpus tests are essential.
- More context may be necessary to bind multi-figure statements, table layouts, exceptions, and cross-references. When unavailable, fail closed rather than manufacture a claim.
- No candidate was promoted; all production mapping and C6 outcomes remain untested for this compact format.
