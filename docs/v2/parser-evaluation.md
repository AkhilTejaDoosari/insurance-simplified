# V2 parser evaluation — plan and decision rule (WP4)

**Pre-registered 2026-11-26, before any candidate was run on the validation set.**
Changing the metrics or the rule after a run needs an owner decision recorded here, with the reason.

## Question
Which PDF reader feeds the engine's document model (`engine/app/schemas/document.py`), and therefore which engine host it needs?

## Candidates
| Candidate | License | Runs where | Status |
|---|---|---|---|
| Current TypeScript reader (pdf.js + `layout-tables.ts`) | Apache-2.0 (pdf.js) | web | Baseline. Needs an export of its pages and tables as the document model (`web/scripts/export-document-model.ts`, WP4 task). |
| pdfplumber | MIT | engine | Adapter in `engine/app/parsing/pdfplumber_reader.py` |
| PyMuPDF | **AGPL-3.0** | engine | Adapter in `engine/app/parsing/pymupdf_reader.py`; evaluation-only dependency group. Shipping it needs an owner decision on AGPL. |

No candidate calls a language model except the hosted ones.

## Data
1. **Synthetic dev fixtures** (in git, generated by `engine/evaluation/synthetic.py`): benefit tables with level columns, two-row headers, wrapped cells, footnotes, an SBC-style question/answer table, a printed page number that differs from the PDF page. Used to build and debug adapters. **Never used for the decision.**
2. **Validation set** (`evaluation/manifests/corpus-v2.json`, split `validation`): the decision is made here, on the answer keys written in WP2.
3. Blind batches are never used for parser choice.

## Metrics (per document type, raw counts)
1. **Table binding** (primary): for every key value that sits in a table, the reader produced a cell with that text whose row label matches the key's benefit label and whose column header path contains the key's level or network tier. Score = bound / keyed values.
2. **Text recall:** key values outside tables found in page text (paragraphs, footnotes, exclusions, conditional clauses).
3. **Reading order:** for keyed passages that span lines, the lines come out in the order the document reads.
4. **Page labels:** printed page detected where the page carries one.
5. **Speed:** p50 and p95 seconds per page on the same machine.
6. **Footprint:** installed size and container image size.
7. **License:** permissive / copyleft / commercial.

## Decision rule
1. Exclude any candidate with a copyleft or commercial license unless the owner has approved that license.
2. Among the rest, pick the highest **table binding** on validation (all types pooled; ties broken by the lowest per-type minimum).
3. It must also be within **2×** the fastest candidate's p95 seconds per page, and no worse than the baseline on text recall.
4. If the top two are within 2 points on table binding, pick the smaller footprint.
5. If no candidate beats the baseline on table binding, keep the baseline reader and record that the engine reads the web app's export.

The chosen reader sets the engine host: a small container (pdfplumber or PyMuPDF) or a container with ML models (Docling). The host choice and its Terraform follow in WP12.

## Real validation run (2026-11-26, 21:00) — 37 validation PDFs (17 SBC, 13 student, 7 travel)

Run with `CORPUS_DIR=… uv run --group parser-eval python -m evaluation.real_run`; every reader in the sandbox.

| Reader | Parsed | Native crashes | Time (37 docs) | SBC structural check (17 SBCs) |
|---|---|---|---|---|
| pdfplumber | 37/37 | 0 | 54 s | deductible 16, out-of-pocket 8, primary care 8, specialist 7, emergency room 4, generic drugs 6 — **49/102** |
| PyMuPDF | 30/37 | **7** (all SBCs, segfault in its table finder) | 151 s | deductible 9, out-of-pocket 7, primary care 4, specialist 4, emergency room 2, generic drugs 3 — **29/102** |

The SBC check is a **structural proxy**, not the answer-key score: it asks whether a value landed in the right row and column of the federal SBC tables, not whether it is the right value.

**What changed to get here** (shared by both readers, `engine/app/parsing/grid.py`): leading banner rows are captions; header rows end at the first value row (money, percent, "no charge", "not covered", copay); merged header cells resolve from above (tall) or from the left (wide); neighbouring physical columns that never hold different text in the same row are merged (readers split one logical column when text shifts); a second label column is used when its rows carry their values further right; wrapped lines merge into the row above. Before these rules the same check scored pdfplumber 6/102 and PyMuPDF 4/102.

**Provisional decision: pdfplumber.** Rule 1 excludes PyMuPDF (AGPL, not approved) and its 7 native crashes on 37 real documents would independently disqualify it. pdfplumber leads on every structural measure and is ~3× faster. Final under rules 2–5 once: (a) answer keys exist for the validation set, (b) Docling has run (needs its models; owner's machine or CI), (c) the TypeScript baseline export exists.

**Engine consequence (done):** readers always run in a separate process (`app/parsing/sandbox.py`) with time, memory and page limits; crashes, hangs and oversize files become typed failures (`crashed`, `timed_out`, `too_many_pages`, `reader_error`).

**Known gaps (next):** out-of-pocket rows and cost-chart rows where the reader merges two table rows into one cell, or splits the chart across pages; student and travel brochures have no shared template, so they are scored only by answer keys.

## Round 2 — all three readers, after two measurement fixes and two engine rules (2026-11-26, 22:45)

Looking at the 30 checks no reader passed showed that most were not reading failures:

* **Measurement (the check itself, `evaluation/real_run.py`, applied to every reader alike):**
  it looked only at pages 1–4 (drug rows are often on page 5+), accepted only columns
  named "network" (plans also say "Participating Provider", "Tier 1 Preferred",
  "Non-IHCP In-Network Provider") and rejected the hyphenated question label
  "out-of- pocket limit" that every reader reproduces faithfully.
* **Engine (`app/parsing/grid.py`, shared by every reader):**
  rule 5 — a table that opens a page with a value row and has the same width as the last
  table of the previous page continues it and takes its header text (no header spans on
  the new page: the page-span guardrail is unchanged); rule 4b — a wrapped label whose
  value is printed on the wrapped line merges into the line above when that line has no
  value.

SBC structural check, 17 validation SBCs × 6 fields = 102. **Rows with "+" are oracle unions: potential coverage if something could always pick the right reader, not an achieved result.**

| Readers | Old check | Check fixed | Rules 4b + 5 only | Both |
|---|---|---|---|---|
| pdfplumber | 49 | 58 | 52 | 61 |
| OpenDataLoader | 64 | 85 | 67 | 88 |
| Docling | 70 | 88 | 73 | **91** |
| pdfplumber + OpenDataLoader (oracle union) | 72 | 93 | 75 | 96 (potential) |
| Docling + OpenDataLoader (oracle union) | 72 | 93 | 75 | 96 (potential) |

The six that remain are the check's vocabulary, by inspection: three plans never use the
word "generic" for their drug tier, and one multi-level plan titles its answer columns by
tier instead of "Answers". No remaining miss is a value the readers failed to read.

Speed on the same 37 PDFs: OpenDataLoader 28 s in total, pdfplumber 54 s, Docling
~2,200 s (CPU). Docling adds nothing on top of pdfplumber + OpenDataLoader here.

**Provisional choice (owner approval needed — OpenDataLoader adds a Java runtime):**
OpenDataLoader for table structure, pdfplumber for page text and spans, both in the
sandbox; Docling kept as the candidate for scanned or image-only pages (it has OCR).
External readers emit no page text in the importer, so their cells get citations only
after their text is located in pdfplumber's page text — the evidence contract is
unchanged. This is a structural check on 6 SBC fields; the decision is final only after
the answer keys (all 37 documents, every value) are scored.

## Round 3 — answer keys and source-grounded reconciliation (2026-11-27)

### What "96/102" was
An **oracle union**: a field counted if any reader bound it. It is potential coverage, not
achieved accuracy. Achieved accuracy needs something that chooses between readers without
the key — the reconciler below — scored against answer keys.

### OpenDataLoader runtime (Java) — facts for the engine service
opendataloader-pdf 2.5.24 (Apache-2.0), one 24 MB CLI jar inside the wheel, needs Java
(tested: OpenJDK 21). Bundled dependencies are MIT/Apache/BSD/ISC plus weak-copyleft
MPL-2.0, EPL-2.0 and CDDL-1.1 (notices to keep; no GPL). Peak memory 555 MB for the
largest validation PDF (13 pages, 5.7 s, JVM start included). Each call starts a JVM, so it
runs one document per call inside the existing parser sandbox (time + memory limits); a
corrupt PDF raises a clean error. No network service is added. Not wired in yet.
