## 2. Actual architecture and execution flow (`integration/m5-m7`)

One Next.js 15 app (React 19, TypeScript). About 19.9k lines in `app/lib`, plus `app/components` and 7 route handlers. Supabase Postgres, pgvector and Storage. Docker on port 3333. Cloud Run was planned but never deployed.

**Upload → result (all synchronous inside HTTP requests; D-016, no queue):**

1. **`POST /api/sessions`** creates an anonymous capability (`session-auth.ts`).
2. **`POST /api/upload`** validates 1–5 PDFs (`MAX_FILES = 5`) and stores the bytes privately (`storage/objects.ts`). Page text comes from pdf.js (`pdf/extract-pages.ts`). The quality gate is in `ingestion/`. Sessions are persisted in Postgres (`session-db.ts`), and page-bounded chunks are embedded into pgvector (`rag/persist-session.ts`, `rag/chunks.ts`).
3. **`POST /api/extract`** (`app/api/extract/route.ts`):
   - **Extraction:** `extractViaLlm` (when `LLM_*` is set) or `extractFallback`.
     - The fallback runs the **fixed 47-fact regex list** (48 rows once the eligibility row is added; the docs call it the 48-fact list) (`extraction/fact-list.ts`) line by line (`findAllMatchesWithHeaders`).
     - It also uses layout tables (`pdf/layout-tables.ts`) and statement claims (`statement-facts.ts`).
     - The LLM path is strict-schema (`llm/client.ts`, `llm-schema.ts`). It is then reconciled, stripped of rows without evidence, and has period candidates checked.
   - **`verifyComparisonTable`** (`verify-table.ts`): plan source verification, citation canonicalization, re-derivation of table anchors, Stage E attribution, and a noise filter.
   - **Sealing:** `sealVerifiedTable` → `issueRows` → `renderIssuedRows` (the evidence core, TB-3 render gate).
   - **Contacts and persistence:** `extractContacts` runs, the result is persisted to `comparison_results` (0005), and presentation groups are proposed.
4. **`POST /api/chat`** (`app/api/chat/route.ts`, `rag/answer.ts`):
   - It loads the stored result **only to scope retrieval** (`scopeDocumentsForChat`), then embeds the question.
   - Retrieval is exact per session (migration 0007, over-fetch 40, RRF in `fusion.ts`), with a usefulness floor before the answer.
   - It then generates an answer or refuses, verifies every quote on its page, and returns.
   - `rag/answer.ts` states the rule: it **must not import extraction**. Chat never answers from the verified grid.
5. **`POST /api/export`** builds a PDF from the stored result. **`/view/...`** is the authorized PDF viewer. **`/api/health`** and **`/api/ready`** report status.

**Plan identity** (`extraction/plan-identity.ts`, 768 lines): recognizes title blocks, FEHB enrollment codes and "Plan (NAME)" declarations, and abstains on anything else.

**Tiers:** column headers (`tiers.ts`, `computeTierHeaders`). There's no grouping of plans across documents: each document is its own plan (roadmap §1).

## 6. Target design (smallest change that reaches V1)

**Monorepo:**
```
web/                 current Next.js app moved as is (git mv), then cut over to the locked design
engine/app/{api,parsing,classification,extraction,verification,schemas,markets,comparison,eligibility,scoring,retrieval,chat,jobs}
engine/tests/        pytest; ported fixtures under tests/fixtures (no real document text)
contracts/openapi.json   exported from the engine; web types generated (openapi-typescript)
evaluation/          manifests, answer-key schema, scorers (data outside git)
infrastructure/terraform/   engine host (after the parser evaluation)
db/migrations/       stays the single migration ledger (0008+ for jobs, facts)
.github/workflows/   web + engine + contract + secret scan + license check
docker-compose.yml   web + engine + local Supabase
```

**Document model (v1, Pydantic):**
- `Document`: `id, sha256, market, currency, language, pages[]`
- `Page`: `number, printed_label, width, height, readable, blocks[], tables[]`
- `Block`: `id, kind, text, bbox, reading_order, footnote_refs`
- `Table`: `id, bbox, header_rows, columns[{id, header_path[]}], rows[{id, label, label_span}], cells[{row_id, col_id, text, span, bbox}]`
- `Footnote`: `marker, text, span`
- Versioned (`model_version`). Every parser candidate emits it.

**Contract (core models):**
- `Candidate`: `benefit_label (document wording), category_key?, value, unit, basis, qualifiers{network_tier, person_level, condition, plan_level}, semantics{negated, exceptions[], conditions[], limits[]}, evidence{value_span, row_label_span, column_header_span, page}`
- `Fact`: `state ∈ {VERIFIED, NOT_COVERED, NOT_MENTIONED, COULDNT_CONFIRM, CONFLICTING}, candidate, key1_result, key2_result, check_page?`
- `PlanIdentity`: `family, level, source_document, evidence`
- `Comparison`: `sections{in_all, in_some, only_one}, rows[group, weight, cells{plan_id → Fact}, markers{differs, different_basis}]`
- `MatchScore`: `plan_id, percent, needs[{need, outcome, fact_ref, scored}], missed_must_haves[], unconfirmed`
- `ChatAnswer`: `route ∈ {comparison, document_fact, calculation, general_term, not_mentioned, refuse}, text, citations[], plans_named[]`
- `Job`: `id, state, progress, checkpoint, error`

**Endpoints:**
- `POST /v1/jobs` (documents → job)
- `GET /v1/jobs/{id}`
- `POST /v1/jobs/{id}/cancel`
- `GET /v1/sessions/{id}/comparison?plans=…&cut=…`
- `POST /v1/sessions/{id}/score`
- `POST /v1/sessions/{id}/chat`
- `GET /health`, `GET /ready`

Every endpoint is authenticated service-to-service; web never exposes the engine.

**Two-key verification:**
- **Key 1 (code):** the span exists on the page; the numbers in the value appear in the span; the row label and value share a row; the column header binds the level and network tier; the basis word is present or derivable from the header or footnote.
- **Key 2 (judge, a different model family):** meaning, including negation, exceptions, conditions, basis and scope.
- **Outcome:** both pass → `VERIFIED`. If either fails → `COULDNT_CONFIRM` with the page, never "not mentioned".

**Jobs:**
- A `jobs` table (Uploaded → Parsing → Extracting → Verifying → Completed / Failed / Cancelled) with a per-document checkpoint, an idempotency key and attempt counts.
- The engine claims a job with `FOR UPDATE SKIP LOCKED`.
- The parser runs in a subprocess with time, memory and page limits.

**Scoring:** from `VERIFIED` facts only; like basis compared with like basis; a need not mentioned by any selected document is excluded from the score and listed.

## 7. Evaluation and acceptance strategy

- **Datasets:**
  - dev fixtures, taken from the 12-document `corpus-v1` dev split
  - validation of at least 15 PDFs: 5 SBC, 5 international student, 5 travel medical, including multi-level documents
  - blind batch A of at least 15, sealed
  - blind batch B of at least 15, sourced and sealed
- **Blocker:** at least 45 public PDFs must be sourced beyond the current 12. Sourcing check first: a type that can't reach 5 + 5 + 5 is not claimed.
- **Parser evaluation (validation set, no LLM):**
  - Candidates: the current TS reader (via a JSON export), pdfplumber, PyMuPDF (AGPL, noted), Docling (needs an ML-model container) and Nemotron Parse. LlamaParse, Reducto and Azure DI are ceiling references.
  - Metrics:
    - table cell binding: the value sits in the cell whose row label and column header match the key's qualifiers
    - recall of paragraphs, footnotes and exclusions
    - reading order
    - coordinate error
    - seconds per page and image size
    - license
  - **Decision rule, written before any run:** the highest table-binding accuracy wins, if it is within 2× the fastest candidate's p95 time and has an acceptable license. Ties go to the smaller image.
- **Gates:** as in V1 scope, with raw counts per type. A system that refuses everything fails on core recall (≥ 95%) and supported answer rate (≥ 95%).
- **Answer keys:** a model pre-fills them and the owner settles every disagreement. The key schema stores every stated benefit and contact, so the in all / in some / only one / not mentioned results can be scored for any combination of documents.

**Risks**

- **Judge false agreement:** two models agreeing on the same wrong reading. Guard: key 1 can't be skipped; blind gates.
- **Engine cold start on the chosen host** vs the 90 s target.
- **Contract drift.** Guard: generated types plus a contract test in CI.
- **Real document text leaking into git** (public repo). Guard: the private-data guard is extended to `engine/` and `evaluation/`.

## 10. Final recommendation

- Proceed with the locked two-service architecture.
- **Keep the web foundations.** Sessions, auth, storage, migrations, viewer and CI are tested and sound.
- **Build the engine new, carrying the repo's best rules over as tests.** Geometry-first tables, the citation matcher, the grammars and exact per-session retrieval are good and worth porting.
- **Retire the checklist core.** The 47-fact list, the line engine and regex-first plan identity are the demonstrated root cause of every generalization failure (§4.1). More tuning won't fix a design that defines in advance what a document should contain.
- **Next:** WP0 on the Mac, then WP1 (consolidation) and WP3 (engine skeleton). WP3 can be built and tested in the cloud workspace on a branch, with no push until the owner approves.
